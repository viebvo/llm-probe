LLM Probe

LLM Probe

Speed, accuracy and capabilities of LLM endpoints

Measures how fast your LLM servers (Ollama, vLLM, Open WebUI, OpenAI-compatible) answer, how well the models do on automatically checked tasks (chat, vision and OCR, tool calling, coding, refusals) and what they can do - with GPU monitoring, stored results and side-by-side comparisons.

◎What it is for

TL;DRA plausibility check for small to mid-sized local models - not a benchmark for flagship models.

Does a model run correctly on your hardware, with your quantization and chat template? And how do your candidates compare on speed and everyday tasks?

Strong models score near the ceiling on most prompts, so the value is in telling local candidates (and broken or degraded setups) apart.

Tip: hover almost anything for an explanation.

⚠What the tests are meant to show

TL;DRSpeed and quality. Speed is self-explanatory; the quality tests check for correct answers and the quality of the response (quality: A wrong answer nobody notices is the worst result - e.g. "I cannot do this" is a good one).

Whether you can trust a model with a task. The worst case in an automated workflow is a wrong answer nobody notices; a model that says "I cannot do this" lets the system call a human.

So the harder tests (log triage, vision) let the model answer unsolvable to questions it cannot answer - and the silent failures gauge shows how many of the answers (also if the question was cut off for some reason) were wrong without a signal a program can catch (exact / signalled / silent). A decoy test (the keyword hidden inside the data) counts false alarms, and a run can use a random code word instead of "unsolvable". More in the README, "What the tests are meant to show" and "Background: a pipeline that can rely on the signal".

▦How to read the gauges

TL;DREvery gauge judges only its own subset of the answers. Red up to 50 %, yellow up to 70 %, green above - like a school test.

A question that cannot be solved on purpose (a stained digit, a detail that is not on the image) does not count towards Vision / OCR. It counts towards Vision: faithfulness: does the model take its answers strictly from the image? The right behaviour there is to read what is really there, or to say unsolvable - not to guess.

Faithfulness is a third, independent indicator next to easy and hard: it splits the missing answers into an honest message and a real miss. Same Vision / OCR, different faithfulness = same reading ability, different behaviour when the image is not enough.

The bar under a dial shows how the tests ended: green right, red wrong, purple aborted or failed, hatched grey not in the test.

1

Add an endpoint

TL;DRTell LLM Probe where your model server lives: a name, the type and the URL are all it needs.

Under Settings > Endpoints (e.g. http://my-server:11434 for Ollama). Optional: an SSH login to the server for GPU and memory monitoring. Test API checks the connection.

2

Select what to test

TL;DRPlan your test thoroughly - it may take up to several hours to complete. Long running tests are not selected by default, so starting your first-ever test by selecting a model and clicking "Start" should be safe enough.

If you want to use all capabilities of this probing tool, read the following:

On the Test page:

  • Endpoint and models. One model or several - several are tested one after another. The model list shows size, quantization and what each model can do (chat, vision, tools); a click on a column header sorts it, the header check box selects. A model's params button holds its own settings (empty = like Whole test); the Q button asks it whether it reasons and which thinking levels it accepts (this loads the model on the endpoint).
  • Prompts, chosen by four filters - language (the standard prompts exist in English, German and Polish; the harder tests and the long sessions are English only), level (standard or harder), group (performance: speed; quality: answers checked automatically, reliability included) and type (text, vision, tools, safety = refusal tests, long sessions) - or by a preset: all speed tests (EN), all quality tests (EN).
  • A new test starts with the standard English text, vision and tool prompts, including the reliability tests (log triage, read versus recall). The harder tests, the refusal tests, the long sessions and the context sweep are off until you tick them (the refusal tests and the sweep ask first).
  • Phases: Single requests and Concurrent load each have a Run this phase switch in their header; a switched-off phase is greyed out.
  • Batch runs: several models, or several comma separated values for max_tokens, temperature, timeout and (Ollama) num_ctx, or several thinking levels, make a batch - every combination is its own run, shown on the start button with an estimated run time. If the endpoint refuses a setting, the batch stops after that message and keeps what is done.
  • Defaults that are fine to start with: max_tokens 32768 (a cap, not a target; not the context size), temperature 1.0, 3 repetitions, load levels 1, 2, 4 and 8.
3

Start

TL;DRPress Start and let it run. The log shows every response live; Abort keeps what was measured.

Start test runs, in this order:

  • warm-up of the model
  • Capability check - always: a few small requests probe vision, tools, reasoning and which settings work. It is the baseline for fair scoring; a prompt that needs a capability the model lacks is not counted.
  • the selected prompts: single requests (cheapest first, so short tests are done before the long ones), then concurrent load, and last the long sessions
4

Look at the results

TL;DROpen a run for its gauges; put several runs side by side in Compare; read what the models actually answered in Responses.

  • Results - lists every run. Mark several to compare, export, import or delete them; add a note; export a PDF; or Reuse for test to load a run's endpoint, models and parameters into the Test page. A run's details show:
    • the quality gauges: chat accuracy, vision / OCR, tool use, coding, answers harmless / refuses harmful and the refusal balance (what was refused: right, or although harmless)
    • the reliability gauges: faithfulness and silent failures (the share of log triage answers that were wrong without a signal)
    • the answer checks (a ∅ marks an answer of unsolvable: on the harder prompts the model may say it cannot answer instead of guessing - it does not change the score), the context sweep, where the time goes, tokens, cost and resources
    • every part is a box you can fold away; your choice stays while you look at the same run or comparison
    • the Prompt set version (the exact wording the run was asked with) next to the program version; runs made with another prompt set are shown in grey
    • a running run is followed live: every 10 s the open details, Compare and Responses refresh (a pulsing dot marks it)
  • Compare - up to 16 runs side by side. Hover a run anywhere - a ranking, a table, a chart - to highlight it everywhere; a click pins it, and Export PDF prints it highlighted.
  • Responses - what the models answered, per prompt and repetition; type in the filter to find a prompt

Under Settings > Prompts you can read all built-in prompts (read-only), copy one into a new prompt of your own and write your own.

If several model servers share the same GPUs, run only the one you test - otherwise they slow each other down.
